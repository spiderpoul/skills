# Критерии аудита

Применяй критерии к конкретному проекту. «Не найдено» после ограниченного поиска — не доказательство отсутствия. Настройки, процессы и фактические результаты проверяй отдельно.

## A. Инструкции и навигация

**A1. Точка входа.** Есть доступная агенту карта ответственности: код/тесты, действующая документация, запуск и проверки. AGENTS.md необязателен, если клиент читает эквивалент. Файл без подключения — артефакт, не рабочая инструкция.

**A2. Границы.** Указаны ограничения, запрещённые обходы и ситуации, требующие решения владельца. Согласованная задача не требует повторного согласования каждого шага; scope не расширяется ради удобства.

**A3. Объём и локальность.** Корень содержит общие сведения; локальные риски расположены рядом с областью. Архитектура, копии правил линтера и процедуры на все случаи не загружаются всегда. Вложенные инструкции согласованы, ссылки существуют.

## B. Документация и актуальные образцы

**B1. Действующее решение.** Понятны применимость, владелец/процесс обновления, код и образец с проверками. Соседний рабочий код не становится стандартом автоматически. Подтверди хотя бы один образец по реализации.

**B2. Legacy и конфликты.** Старый подход отделён от нового с причиной и границами совместимости. При конфликте docs и кода выясняют актуальность; «документация всегда права» без проверки не устраняет устаревание.

**B3. Подводные камни.** Риск связан с наблюдаемым последствием и проверкой. Примеры: маршрут → старые ссылки → прямой вход/reload; общий API → потребители → контрактные сценарии. Применяй их только при соответствующем риске.

**B4. Одна версия правила.** Инструкции, задачи и скиллы ссылаются на общую документацию. Wiki допустима, если доступна агенту и привязана к действующему коду/контракту; недоступный источник оставляет пробел доступа.

## C. Задачи, scope и приёмка

**C1. Постановка.** Для заметного изменения до кода описаны цель, поведение, ограничения и вне scope. Для небольшой правки достаточно тикета/плана; не требуй спеку на опечатку.

**C2. Сценарии.** Критерии проверяемы: успешный результат, значимые ошибки, пустые состояния, восстановление и совместимость. Состав определяется задачей. «Сделать как рядом» и «всё работает» оставляют неоднозначность.

**C3. Контракты и вопросы.** Зафиксированы существенные API, маршруты, права, идентификаторы и потребители. Неясные продуктовые решения отмечены для владельца, не придуманы агентом. Markdown/трекер/иной доступный формат допустим.

**C4. Решение человека.** У существенных решений есть статус и ответственный до реализации. «Согласовано» в файле — заявление; историю подтверждай отдельно при доступности. Недоступная история не доказывает отсутствие согласования.

**C5. Поведение и план.** Приёмка отличима от шагов реализации. Команды могут быть в tasks/docs, если маршрут от требования до проверки сохраняется. Документы обновляются вместе с кодом.

## D. Cross-zone и владельцы

**D1. Влияние.** Для общего кода/контрактов прослеживается «меняешь → кто зависит → что проверить». Таблица необязательна; граф, тесты и docs могут выполнять ту же функцию.

**D2. Потребители.** Проверки охватывают зависимые зоны, а не только изменённый пакет. Для конфига — сборки потребителей; UI/API — экраны/клиенты. Строковая эвристика не равна полному графу зависимостей.

**D3. Ответственность.** Можно найти владельца критичной зоны и получить ревью. CODEOWNERS маршрутизирует, а обязательный approval определяется настройками платформы. Недоступные настройки оставляют enforcement непроверенным.

## E. Проверки и Definition of Done

**E1. Воспроизводимость.** Команды существуют в текущей конфигурации; среда и данные описаны. У каждой проверки понятны подтверждаемое свойство и ограничения.

**E2. Честный результат.** Gate проверяет условие; ошибка не маскируется `|| true`, безусловным успехом, перезаписанным exit code или потерей результата подпроцесса. Необязательная диагностика с явным статусом отличается от обязательного gate.

**E3. Полнота.** Важный критерий связан с тестом либо повторяемым сценарием. Build не подтверждает поведение, безопасность, производительность и интеграцию. Для UI по риску нужны консоль/сеть, прямой вход, ошибки/восстановление; для сервиса — API/интеграционные сценарии.

**E4. Защита проверок.** Правила изменения ожиданий, baseline и бюджетов препятствуют подгонке под зелёный результат. Фактическое ревью этих путей подтверждай при доступности. Ослабление проверки не исправляет регрессию.

**E5. Производительность.** Если задача имеет такой риск, замер имеет baseline, сборку, данные, сценарий и сопоставимые условия. Для сервиса проверяй значимые задержки/ресурсы, для CLI — соответствующий объём данных и время работы. Во фронтенде загрузка, рендер и память подтверждают разные свойства; локальные LCP/CLS не доказывают полевой UX/INP. Выбирай инструменты и бюджеты самого проекта.

**E6. Отчёт.** Есть команды, существенный вывод, результаты и непроверенное. Код 0 не всегда подтверждает предмет проверки: выясни семантику инструмента. Недоступная обязательная проверка остаётся ограничением.

## F. Инструменты и диагностика

**F1. Доступность.** Агент получает задачи, docs, код, CI и диагностику в разрешённой среде. Для UI можно наблюдать приложение; MCP необязателен. Настройка не подтверждает рабочее подключение.

**F2. Данные и права.** У инструментов понятны разрешения и назначения передачи данных. Внутренняя модель не гарантирует закрытый контур: учитывай MCP, CLI, телеметрию/логи. Проверяй обнаруженные конфигурации; не утверждай утечку без доказательства.

**F3. Диагностика.** Длинный вывод сокращается скриптом/поиском без потери первой ошибки и корреляции. Ответ содержит доказательства причины и неизвестное, а не весь лог или уверенную догадку.

## G. Скиллы

**G1. Потребность.** Процедура обслуживает повторяющуюся задачу/промах. Отсутствие скиллов не дефект; множество тоже. Избыточность доказывай пересечением условий/конфликтами, пользу — примерами работы.

**G2. Контракт.** Description объясняет применение и результат. Тело задаёт вход, шаги, стоп-условия, выход и завершение. Общий DoD не копируется; локальные критерии проверяют результат процедуры.

**G3. Поддерживаемость.** У общего скилла есть ответственный и процесс обновления; реестр/метаданные помогает выбирать. Повторяемая детерминированная обработка вынесена в скрипт, длинные сведения доступны по ссылке.

**G4. Состав.** Скиллы не дублируют docs/друг друга; избыточные удаляются/объединяются. Импортированные инструкции и скрипты прочитаны и адаптированы к проекту. Нет доказательства пользы — неизвестное, не автоматическое требование удаления.

## H. Субагенты и ревью

**H1. Применимость.** Помощник изолирует исследование, длинный вывод или независимое ревью. Простому проекту он необязателен. Не требуй ролевую цепочку PM → архитектор → dev → QA.

**H2. Передача.** Есть узкий вход, исходные требования, допустимые инструменты, компактный выход с доказательствами/неизвестным. Требования не заменяются пересказами; за результат отвечает основной исполнитель.

**H3. Ограничения.** «Только читает» в тексте — инструкция. Проверь клиентские права, включая Bash/MCP; запрет Edit не закрывает запись через Bash. Не называй настройку изоляцией без основания.

**H4. Независимость.** Ревьюер не исправляет/одобряет собственный результат. Один исполнитель и помощники на чтение — простой начальный вариант; несколько писателей допустимы при изоляции зон, контролируемой интеграции и независимой проверке.

**H5. Ревью.** Находка опирается на контракт, дефект или воспроизведение. Для критичных путей есть профильные проверки/владелец. Агентный комментарий не подменяет требуемое решение человека и не разрешает merge.
